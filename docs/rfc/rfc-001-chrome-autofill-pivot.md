## 0. RFC-002 取り込みメモ（2026-06-11）

RFC-002 の要件を本ドキュメントへ統合した。大半は整合しており、そのまま取り込んだ
（目的/非目的、想定ユーザー、ユースケース、更新ステータス管理、更新ページURL登録、ユーザーメモ、
段階的フォーム検出、サイト別ルール、MVP範囲、リスク、成功指標、非機能要件）。

相違が2点あり、次の通り判断した。

| 論点 | RFC-002 | RFC-001（旧） | 採用 |
| --- | --- | --- | --- |
| サイト一覧の源泉 | Chrome Password Manager の保存URL | autofill 観測で蓄積 | **観測を一次、手動追加/インポートを補完**。拡張APIから Password Manager の保存URL一覧は取得できない（RFC-002 §12.1 も同リスクを認識）。 |
| 値の保存 | 個人情報を一切永続保存しない | カテゴリ別に軽量な識別値のみ保存 | **カテゴリ別方針を維持**。「古い住所が残るサイトの絞り込み」（RFC-002 §7.1 のユースケース）には識別値（郵便番号・電話下4桁）が必要。カード番号・パスワード・電話フル桁は保存しない原則は厳守。 |

また RFC-002 §8.5「ユーザーが発見した更新ページURLを保存し次回以降優先表示」が、
未解決だった **P1（住所変更ページURLへの到達方法）の答え**になったため、P1 は解決とした（§6b）。

## 0b. 壁打ち完了時点のサマリ（2026-06-11）

### 合意したこと

- 製品の再定義: Chrome に保存＋自動入力を任せ、formfill-assistant は **「どのサイトにどの種別を入れたか」を
  サービス単位で一元管理するインベントリ／管理ハブ** を担う（§2, §4）。
- 検知方式の軸: **`:autofill` 擬似クラス＋イベント観測**でフィールドを捕捉し、**#9 scanner / #10 分類器を
  転用**して種別判定。値は基本持たない（§3）。
- データ方針: カテゴリごとに保存/表示を出し分け（名前=フル, 電話=下4桁, 住所=郵便番号, カード・ID書類・
  パスワード=保存せずリンクのみ）。サイト粒度は**オリジン**で確定（§5）。
- 「高精度自動入力」= 動的スキーマ／カスタム種別の復活（§5）。
- 変更伝播フローは **HITL の半自動**で実現可能と確認（拡張は遷移・フォーカス・観測のみ、入力=Chrome
  autofill、保存=ユーザー）。**assisted manual change は許容 / automatic bulk change は非対象**（§6b, §9）。
- **P1 解決**: 更新ページURLは「ユーザー登録URL → 観測URL → トップページ」のフォールバック連鎖で到達
  （RFC-002 §8.5 を採用、§6b）。
- サイトごとの**更新ステータス管理**（未確認/更新必要/更新済み 等）と**ユーザーメモ**を導入（§6c）。
- MVP範囲・リスク・成功指標を確定方向で記載（§11〜§13）。
- **P2 解決**: 「古い住所のサイト」の絞り込みは値比較ではなく**変更イベント（キャンペーン）モデル**で行う
  （宣言時刻 T 以降に新値で再観測されていないサイト＝更新必要）。新値の取得は
  「統合編集画面での保存 / 初回観測の確認 / 手動入力」の3層フォールバック（§6d）。
- **統合編集画面（ゼロ保持の編集バッファ）構想**を追加。Chrome 側データの読み書きはユーザー媒介
  （autofill 発動＋Chrome の保存プロンプト）で行う。成立性は要PoC = **R2**（§6e）。

### 次のアクション

- **R / R2 の PoC は Issue #29 へ切り出し済み**: `chrome://` リンクの成立性（R）と、拡張ページ上での
  Chrome autofill 発動＋保存プロンプト動作（R2）を、同じ PoC 拡張で実機検証する（§6, §6e）。
- PoC 結果を §6 / §6e / §10 に反映して外部リンク方式と統合編集画面の形を確定し、その後
  「正式docs更新Issue」と「実装Issue群」へ分割する。

### PoC 後に残る問い

## 1. 背景 / きっかけ

Chrome に、電話番号・メールアドレス・住所・生年月日・勤務先住所・クレジットカード情報などを
自動入力する機能が標準搭載された。これにより formfill-assistant が自前で「保存＋入力」を担う
価値が薄れた一方、Chrome には **「どのサイトに、いつ、どの種類のデータを入力したか」を一覧化する
機能がない**。ここを formfill-assistant で補完する。

ユーザー側の課題（引っ越し・電話番号変更などの場面）:

- どのサイトに古い住所や連絡先が登録されているか把握しづらい。
- Chrome autofill はフォーム入力を補助できるが、複数サイトの登録情報を横断的に管理・更新する機能はない。
- Chrome Password Manager はログイン情報を保持しているが、登録済みサイトのプロフィール情報更新までは扱わない。
- サイトごとにフォーム構造や更新画面の導線が異なるため、更新漏れが発生しやすい。
- 個人情報を独自アプリにフルで保存すると、セキュリティリスクと信頼性の問題が大きい。

このため本製品は「個人情報そのものを保持する」のではなく、Chrome の既存機能を前提に、
ユーザーが安全に登録情報の更新を進められる補助ツールを目指す。

## 2. 新しい製品ポジション

- **Chrome に任せる**: 個人情報・支払い情報の **保存** と **自動入力**（Chrome標準 autofill を借用）。
- **formfill-assistant が担う**: Chrome autofill の **入力記録 / 監査レイヤ**＋**更新支援ハブ**。
  「いつ・どのサイトに・どの種別のデータを入れたか」をローカルに一覧化し、
  更新が必要なサイトの可視化・到達・記録を支援する。

### 目的

- 更新すべき可能性のあるサイトを可視化し、更新漏れを減らす。
- Chrome autofill を使った入力作業を補助する（入力自体は Chrome が行う）。
- サイトごとの更新画面への到達を支援する。
- 機微情報をアプリ側で保持しないことで、セキュリティリスクを抑える。

### 非目的

少なくとも初期段階では次のことを目的としない。

- 各サイトの登録情報を完全自動で更新すること。
- ユーザーの同意なしにサイトへログインすること。
- ID・パスワードを取得・保存・送信すること。
- クレジットカード番号などの機微情報をアプリ側で保存すること。
- サイトの利用規約に反するスクレイピングや自動操作を行うこと。
- Chrome autofill や Chrome Password Manager を置き換えること。
- 金融機関や行政サービスなど高リスクサイトの自動更新を行うこと。

### 想定ユーザー

- 引っ越しに伴い、多数のWebサービスで住所変更が必要な人。
- 複数のECサイトや会員サイトを利用している人で、登録情報の更新漏れを避けたい人。
- Chrome autofill / Chrome Password Manager を日常的に利用している人。
- 自分の個人情報を新しいアプリに保存することには抵抗がある人。

## 3. 検知方式（論点A）— 合意した軸

拡張機能は Chrome autofill API を直接は使えないが、以下で観測する：

- **`:autofill` 擬似クラス**（旧 `:-webkit-autofill`）で「そのフィールドが Chrome により自動入力
  されたか」を判定できる（`el.matches(":autofill")`）。
- autofill 発生時に `input` / `change` イベントも飛ぶため、**発生タイミングと対象フィールドを観測可能**。

### 重要な制約

- クレジットカード等の機微フィールドは、**ユーザー操作前は値を JS から読めない / マスクされる**
  ことがある。→ **実値の取得は前提にしない**。
- 取れるのは「autofill された事実 / 時刻 / サイト（URL・ドメイン）/（分類による）データ種別」。

### 既存資産の転用

- #9 scanner（`scanFields`）と #10 分類ロジックは、**「fill するため」→「autofill されたフィールドを
  観測・分類して記録するため」** に転用できる見込み。捨てない。

### 種別分類の段階（RFC-002 §11.2 を採用）

種別判定は決定的なルールベースで、次の段階で行う。

1. `autocomplete` 属性による検出
2. `label` / `placeholder` / `name` / `id` によるルールベース検出
3. 日本語・英語のキーワード辞書による検出
4. DOM構造（周辺テキスト・フォーム文脈）に基づく補助判定
5. ユーザーによる手動補正

検出結果には信頼度を付け、ユーザーが補正できるようにする（誤分類前提の設計）。

### この軸の決定

> **`:autofill` 擬似クラス＋イベント観測でフィールドを捕捉 → #9/#10 を転用して種別を分類 →
> メタデータ（いつ/どこ/種別）として記録。値は保存しない。**

## 3b. サイト一覧の源泉（RFC-002 §8.1 との統合）

RFC-002 は Chrome Password Manager の保存URLを一覧の起点に置いたが、**拡張APIから保存URL一覧は
取得できない**（`chrome.passwordsPrivate` は拡張に公開されていない。RFC-002 §12.1 も同リスクを認識）。
よって次の構成とする。

- **一次ソース: autofill 観測**。各サイトで autofill を観測した時点でレコードを自動作成する（§3）。
- **補完: ユーザーによる手動追加・削除**。観測前のサイトもユーザーが対象に追加できる。
- **将来候補（必要になったら）**: ブックマーク・履歴からの候補提示、Chrome のパスワードエクスポート
  CSV のインポート。MVPには含めない。

一覧の整理要件（RFC-002 から採用）:

- サイトはオリジン単位で集約し、重複を統合する。
- 明らかに対象外のサイトをユーザーが除外・非表示にできる。

## 4. 製品の最終UIイメージ

「いつ入れたかの時系列ログ」ではなく、**サービスごとの『何が保存されているか』のインベントリ
（ダッシュボード）＋公式管理画面へのショートカット**を目指す。

| サービス（名前＋アイコン / クリックで遷移） | 名前 | 電話 | 住所 | カード | ログイン | ステータス |
| --- | --- | --- | --- | --- | --- | --- |
| Coursera | 山田太郎 | …1234 | 〒150-0001 | → Google Wallet | → password-manager 詳細 | 更新済み |

- 行ヘッダはサービス名＋favicon。URL列は出さない。サービス名クリックでそのサイトへ。
- カード・パスワードは**値を持たず、公式管理画面へリンクするだけ**（最も機微なものは保存しない）。
- 名前・電話下4桁・郵便番号など**識別用の軽い値だけ**表示する。
- ステータス・カテゴリで絞り込めること、サイトごとに「次に取るべき操作」が分かることを要件とする
  （RFC-002 §9.3）。
- Chrome 側で編集すべき情報（autofill の元データ）と、サイト側で更新すべき情報（各サイトの登録値）を
  UI上で区別して見せる。アプリが個人情報をフルで保持しているように見えない UI にする（RFC-002 §9.3, §12.3）。

## 5. 記録データのスコープ（論点B）— カテゴリごとに方針を分ける

「メタデータのみ(案X)」「一部の値(案Y)」の二者択一ではなく、**機微度に応じてカテゴリ単位で使い分ける**。

> RFC-002 は「個人情報を一切永続保存しない」としたが、「古い住所が残るサイトの絞り込み」
> （RFC-002 §7.1）の実現には比較可能な識別値が必要なため、**軽量な識別値（郵便番号・下4桁等）に限り
> 保存する**本方針を採用する。カード番号・パスワード・電話フル桁・住所全文は保存しない原則は共通。

Chrome の保存カテゴリを表示方針でグルーピングする。基本は「Chrome が保存しうる種別はすべて列に
出せる」方針だが、機微情報は値を持たずリンクのみ。

| グループ | 種別 | ローカル保存 | 表示 / リンク |
| --- | --- | --- | --- |
| 連絡先 | 名前 | フル | フル表示 |
| 連絡先 | 性別 | フル | 表示 |
| 連絡先 | メール | （要検討: フル/マスク/ドメイン） | 表示 |
| 連絡先 | 電話 | **下4桁のみ** | …1234 |
| 連絡先 | 生年月日 | （要検討: 年のみ等） | 表示 |
| 連絡先 | 自宅住所 / 勤務先住所 / 配送先住所 / 請求先住所 / その他住所 | **郵便番号のみ** | 〒… |
| 高精度自動入力 | 任意フォーム項目（= 動的スキーマ / カスタム種別） | （種別ごとに判断） | 観測した種別を動的に列追加 |
| 支払い | クレジットカード | **保存しない** | → Google Wallet (`https://wallet.google.com`) |
| ID書類 | 運転免許証 / IDカード / パスポート | **保存しない** | → Chrome の該当管理画面リンク |
| 認証 | ユーザー名 / パスワード | **保存しない**（ドメインのみ） | → パスワードマネージャー詳細 |

- 「高精度自動入力」は元の formfill-assistant 要件にあった**動的スキーマ / カスタム項目**の復活。観測した
  未知種別を動的に列として追加する。
- 配送先住所 / 請求先住所はサイト側のフォーム文脈で区別される種別として観測する（RFC-002 §8.2）。
- 値の出どころは **Chrome の住所録ではなく「各サイトでの autofill 観測」**。拡張は Chrome の保存内容を
  直接読めないため、列の全体像は「これまで観測した種別の和集合」、各サイト行はその部分集合。

レコードは **サービス（オリジン）単位のインベントリ（サマリ型）** を基本とする。同一(オリジン×種別)は
最新値で上書き。時系列の履歴を持つかは Open Question。

データモデル（暫定。RFC-002 のステータス・メモ・更新ページURLを統合）:

```ts
type UpdateStatus =
  | "unchecked"      // 未確認
  | "needsUpdate"    // 更新必要
  | "noUpdateNeeded" // 更新不要
  | "updated"        // 更新済み
  | "cannotLogin"    // ログイン不可
  | "manualCheck"    // 手動確認が必要
  | "excluded";      // 対象外

interface ServiceRecord {
  origin: string;        // 例: https://www.coursera.org（サイト粒度=オリジンで確定）
  serviceName: string;   // 表示名。autofill 検知時の document.title から導出する案
  updatedAt: number;
  status: UpdateStatus;  // 更新作業の状態（§6c）
  lastCheckedAt?: number; // ユーザーが最後に確認した日時
  updatePageUrl?: string; // ユーザーが登録した更新ページURL（§6b P1）
  note?: string;          // ユーザーメモ
  entries: CategoryEntry[];
}

interface CategoryEntry {
  category: "name" | "phone" | "address" | "creditCard" | "login";
  displayValue?: string; // name=フル, phone=下4桁, address=郵便番号。card/login は持たない
  observedAt: number;    // このカテゴリを最後に観測した時刻。変更キャンペーンの完了判定に使う（§6d）
  // creditCard -> Google Wallet, login -> password-manager 詳細リンク（origin から生成）
}
```

保存しない情報（RFC-002 §8.6 / §11.1 を採用・厳守）:

- 住所全文 / 電話番号フル桁
- クレジットカード番号
- ユーザー名・ID・パスワード
- 機微フィールドの実値全般

## 6. 外部管理画面へのリンク（要検証の最重要リスク）

- **カード**: Google Wallet（`https://wallet.google.com` ないし `https://pay.google.com`）。https なので問題なし。
- **ログイン**: Chrome パスワードマネージャーの詳細（例: `chrome://password-manager/passwords/coursera.org`）。
  - **`chrome://` URL は拡張機能 / Web ページからのリンク・遷移が原則ブロックされる**。`chrome.tabs.create()`
    でも多くの `chrome://` は弾かれる。**この成立性が製品の中核**なので、PoC で実機検証してから設計を確定する。
  - 開けない場合のフォールバック（URL のコピー表示 / 案内文 等）を用意するか、Open Question。
- **Chrome autofill 設定画面への導線**: ユーザーが autofill の元データ（住所・連絡先）を編集する場面では
  Chrome の設定画面（住所その他 / お支払い方法）へ誘導する（RFC-002 §8.3）。これも `chrome://settings/...`
  リンクの成立性と同じ PoC で検証する。
- **favicon / サービス名**: MV3 の `favicon` 権限＋ `_favicon/?pageUrl=` で取得（要 permission 追加・docs 記載）。
  サービス名は autofill 検知時の `document.title` を記録するのが最も確実。

## 6b. 変更伝播フロー（HITL）— ユーザーが描いた中核体験

「Chrome で住所を変えたら、古い住所が残るサイトを一元管理して直したい」を、**自動一括変更ではなく
human-in-the-loop の半自動**で実現する。拡張がやるのは遷移・フォーカス・観測の3つだけで、入力は
Chrome autofill、認証・削除・保存はユーザーが行う。

想定フロー:

1. ユーザーが Chrome 連絡先情報で新住所を保存する。
2. ユーザーが formfill-assistant で「住所が変わった」を宣言（変更キャンペーン開始、§6d）。
   **T 以降に新住所で確認できていない全サイト**が「更新必要」としてフィルタ一覧される
   （拡張は Chrome の現住所を読めないため、値比較ではなく宣言時刻との比較で絞り込む）。各行に
   **変更ボタン**と**更新ステータス**（§6c）。
3. 行の変更ボタン → そのサイトの住所変更ページへ遷移。
4. ログインを求められたら Chrome のパスワード/ID autofill でログイン。再認証/MFA/確認メールは
   **ユーザー本人**が対応。
5. 住所欄に自動フォーカス → ユーザーが旧住所を削除 → Chrome autofill が新住所を入力 →
   **保存ボタンはユーザーが押す**。
6. 新住所が入った事を formfill-assistant が観測 → 一覧の郵便番号を最新化、ステータスを「更新済み」に。
7. 一覧に戻り、他サイトで 3〜5 を繰り返す。

### 安全境界の判定

| 項目 | このフロー | 判定 |
| --- | --- | --- |
| フォーム自動送信 | 保存はユーザーが押す | OK |
| 拡張による値入力 | 入力は Chrome autofill。拡張はやらない | OK |
| ログイン/MFA | ユーザー本人 | OK |
| 複数サイト「自動」変更 | サイトごとにユーザー主導の手動変更 | 「自動一括」ではない |

→ **assisted manual change（人間主導の手動変更を補助）= 許容**、**automatic bulk change（自動一括変更）
= 引き続き非対象** を docs で明確に線引きする必要がある（現 CLAUDE.md は後者のみ禁止と記載）。

### P1: 更新ページURLへの到達 — 解決（RFC-002 §8.5 を採用）

観測したURLは多くの場合チェックアウト/登録フォームで、アカウント設定の編集ページとは別URLになる。
次のフォールバック連鎖で解決する。

1. **ユーザーが登録した更新ページURL**（`ServiceRecord.updatePageUrl`）があれば最優先で開く。
   ユーザーが正しい更新ページを発見したら、その場で保存できる導線を用意する。
2. なければ **autofill を観測したURL** を初期候補として開く。
3. それもなければ **オリジンのトップページ** に遷移し、ユーザーが導線をたどる。

### P2: 「古い住所のサイト」を絞る比較の土台 — 解決（§6d）

値比較ではなく**変更イベント（キャンペーン）モデル**を採用した。詳細は §6d。

### 残る前提（要検討）

- **P3: 権限。** 全サイトへの content script（検知・フォーカス・観測）＋タブ遷移制御が必要。ホスト権限
  拡大を manifest と docs に明記。

## 6c. 更新ステータス管理（RFC-002 §8.6 を採用）

サイトごとに更新作業の状態を管理する。ステータスは `ServiceRecord.status`（§5）の7値:
**未確認 / 更新必要 / 更新不要 / 更新済み / ログイン不可 / 手動確認が必要 / 対象外**。

- 「更新済み」への遷移は、§6b の観測による自動更新と、ユーザーによる手動記録の両方を許す
  （観測できないサイト・電話や郵送で変更したサイトもあるため）。
- 最終確認日時（`lastCheckedAt`）とユーザーメモ（`note`）を併せて記録する。
- 一覧はステータス・カテゴリで絞り込める（§4）。

## 6d. 変更イベント（キャンペーン）モデル — P2 の解決

「古い住所のサイト」の絞り込みは、郵便番号の**値比較**ではなく、**「住所が変わった」という宣言時刻 T
との比較**を土台にする。値の比較が不要なので「拡張は Chrome の現住所を読めない」制約と無関係に成立し、
郵便番号が変わらない引っ越し（同一建物内・近所）でも漏れない。

- ユーザーが「住所が変わった」を宣言（カテゴリ指定: 自宅 / 勤務先）→ **変更キャンペーン**開始。
- **T 以降に新値で再観測されていないサイトは、すべて「更新必要」**（§6c のステータスへ反映）。
- 新郵便番号が分かる場合は、T 以降の観測値との照合で「更新済み」へ**自動遷移**させる。
  つまり郵便番号の役割は「絞り込みの土台」ではなく**完了検証**。

新値の取得は3層のフォールバック:

1. **統合編集画面の保存ボタン**（§6e）— 保存と同時に T と新値が揃う（R2 の PoC 成立が前提）。
2. **初回観測の確認** — キャンペーン開始後、最初のサイトで観測した新郵便番号を
   「〒XXX-XXXX を新しい住所として扱いますか？」とユーザーに確認して基準値化する。
3. **手動入力** — ユーザーが新郵便番号（軽量値のみ）を一度入力するショートカット。

```ts
interface ChangeCampaign {
  category: "address" | "phone" | "email"; // 住所以外（電話・メール変更）にも汎用
  startedAt: number;        // T。これより前の観測は「旧値の疑い」
  newDisplayValue?: string; // 任意。住所=郵便番号, 電話=下4桁。完了検証に使う
  confirmedBy?: "editScreen" | "observation" | "userInput";
}

type CampaignJudgement =
  | "needsUpdate"    // 旧値の疑い → ステータス「更新必要」
  | "updated"        // 新値で確認済み → 「更新済み」へ自動遷移
  | "manualCheck"    // 自動では確定できない → 「手動確認が必要」
  | "notApplicable"; // 対象カテゴリの観測なし

function judge(rec: ServiceRecord, c: ChangeCampaign): CampaignJudgement {
  const entry = rec.entries.find((e) => e.category === c.category);
  if (!entry) return "notApplicable";
  // キャンペーン対象カテゴリ自体が T 以降に再観測されていなければ旧値の疑い。
  // レコード単位の updatedAt では判定しない（別カテゴリの観測で誤完了するため）。
  if (entry.observedAt <= c.startedAt) return "needsUpdate";
  // 新値が分かっている場合のみ、照合して「更新済み」へ自動遷移させる
  if (c.newDisplayValue) {
    return entry.displayValue === c.newDisplayValue ? "updated" : "needsUpdate";
  }
  // 新値が不明なら自動完了させず、確定はユーザーの手動記録（§6c）に委ねる
  return "manualCheck";
}
```

- 完了判定は**キャンペーン対象カテゴリ自体の再観測**（`CategoryEntry.observedAt`、§5）を必須とする。
  レコード単位の `updatedAt` で判定すると、住所キャンペーン中に電話欄の観測などで誤って完了扱いに
  なるため使わない。
- 新値が不明な間は「更新済み」への自動遷移を行わない（誤完了より見逃しの少なさを優先）。
  §6d の3層フォールバックで新値が確定し次第、自動遷移を有効化する。
- 電話番号・メール変更にもそのまま使える汎用モデル（RFC-002 §8.2 の更新カテゴリ全般と整合）。

## 6e. 統合編集画面（ゼロ保持の編集バッファ）— 構想

Chrome では連絡先情報・パスワードマネージャー・支払い方法・IDドキュメント・autofill 設定が**別々の
ページ**に分かれており、自分のデータ全体を一覧できない。formfill-assistant にこれらを**一画面で編集
できる統合編集画面**を置く。ただしデータは保持しない:

> 編集時に Chrome 側から値を取得 → 編集バッファ（メモリ上のみ）で編集 → 保存ボタンで Chrome 側へ
> 保存 → formfill-assistant 上のデータは全て破棄。

- 保存ボタン押下 = **変更キャンペーンの開始トリガー**（§6d の層1）。T と新値が同時に揃うため、
  住所が新しくなったことの検知にもなる。
- ゼロ保持（編集バッファのみ・永続保存なし）は §5 / §7 のデータ方針と整合する。

### 実現方式 — 直接APIは無いため、ユーザー媒介（HITL）で行う

`chrome.autofillPrivate` / `chrome.passwordsPrivate` は `chrome://settings` 専用の非公開APIで、
一般拡張からは読みも書きもできない。よってユーザー操作を媒介にする:

- **読み**: 編集画面に住所フォームを置き、**ユーザーが Chrome autofill を発動**して値を流し込む
  （ユーザー同意つきの読み取りと等価）。
- **書き**: 編集後のフォーム送信時に Chrome が出す**「住所を更新しますか？」保存プロンプト**に委ねる
  （保存主体は Chrome とユーザー。拡張は書かない）。
- どちらも `chrome-extension://` ページ上で動作するかが未検証 → **R2（要PoC）**。
  R（`chrome://` リンク）と同じ PoC 拡張で一度に検証する。

### PoC 失敗時の縮退形

- 統合編集画面は「**Chrome データの統合ランチャー**」に縮退する: 連絡先 / パスワード / 支払い /
  IDドキュメントの各設定ページへの導線を一画面に並べる（R の `chrome://` リンク成立性に依存）。
- そこに「変更を宣言する」ボタン＋新値（郵便番号などの軽量値のみ）の一時入力欄を添え、
  キャンペーン開始UIとしては維持する（§6d の層3）。

### 対象範囲

- PoC・編集対象は**連絡先カテゴリのみ**。パスワード・カードは読み書きとも行わず、リンクのみ
  （§5 / §9 の既存方針を維持）。

## 7. プライバシー / セキュリティ（論点C）

記録自体が新たな機微情報。要件レベル（暗号化 / 保持期間）は未確定だが、RFC-002 §9 から
次を要件として採用する。

- ローカル保存のみ。外部サーバーへの送信・テレメトリは行わない。将来サーバー連携を行う場合は
  明示的な同意を必須とする。
- ID・パスワード・カード番号・電話フル桁・住所全文を保存しない（§5）。
- 一時的に取得した値はメモリ上のみで扱い、ログ・エラー情報に個人情報を出力しない。
- 必要最小限の権限のみを要求し、権限は明示的に説明する（P3 と接続）。
- 初回起動時に、権限と「何を保存し、何を保存しないか」のデータ方針を明示する（§12.3 の誤解対策）。
- ユーザーが記録対象サイトを除外でき、保存済みメタデータをサイト単位・全体で削除できる。
- 暗号化 / 保持期間 / エクスポート / allow-deny リストの要件レベルは Open Question のまま。

なお、名前・電話下4桁・郵便番号をローカル保存することは、「保存はChromeに任せる」からの**部分的な後退**。
カード番号・パスワード・電話フル桁は保存しないことで「カード情報非保存」原則とは両立する（§0 の採用判断）。

法的・規約面（RFC-002 §9.5）:

- 各サイトの利用規約に反する自動操作・スクレイピングを行わない。ユーザーの明示的操作を重視する。
- 金融・行政・医療系サイトは慎重に扱う（初期対象に含めるかは Open Question）。

## 9. 維持する安全境界（更新）

- フォーム自動送信しない / CAPTCHA・MFA・bot検知・アクセス制御を bypass しない /
  同意・契約を自動チェックしない。
- パスワードとカード番号は読み取らない / 保存しない。
- ユーザーの同意なしにサイトへログインしない。サイトの利用規約に反する自動操作をしない。
- **assisted manual change は許容**（遷移・フォーカス・観測のみ。入力=Chrome autofill、保存=ユーザー）。
  **automatic bulk change（拡張が値を書いて送信まで行う自動一括変更）は非対象のまま。**
- 高リスクサイト（金融・行政・医療系）では自動化（遷移・フォーカス）をさらに制限する。

- **R2（最重要・Rと同一PoCで検証）**: `chrome-extension://` ページ上で Chrome autofill の発動と
  「住所を更新しますか？」保存プロンプトが動作するか（§6e）。結果で統合編集画面の形を確定する。
- **P3**: 全サイト content script ＋タブ遷移に伴うホスト権限の範囲と最小化。
- A': Chrome autofill とユーザー手入力を区別する必要はあるか / できるか（特に下4桁・郵便番号の抽出）。
- B': インベントリ（最新値上書き）に加えて時系列履歴も持つか。将来ステータスを同期するか。

## 11. MVP範囲（RFC-002 §10 を採用・調整）

### 含めるもの

- Chrome 拡張（MV3）として実装。
- autofill 観測によるサービスレコードの自動作成（§3, §3b）＋ユーザーによる手動追加・削除・除外。
- オリジン単位のインベントリ一覧UI（§4）。
- サイトごとの更新ステータス管理・最終確認日時・ユーザーメモ（§6c）。
- カテゴリの観測ベース表示＋手動補正（§5）。
- 更新ページURLの登録と優先表示（§6b P1）。
- 変更イベント（キャンペーン）の宣言と「更新必要」フィルタ・完了検証（§6d）。
- 統合編集画面 または 統合ランチャー（§6e。R / R2 の PoC 結果で形を確定）。
- Chrome autofill 設定画面・Google Wallet・パスワードマネージャーへの導線（§6。`chrome://` は PoC 結果次第）。
- ルールベースのフォーム種別検出（§3 の段階1〜3を中心に）。

### 含めないもの

- 完全自動ログイン / 完全自動送信 / 自動一括変更。
- ID・パスワードの取得、カード番号の保存。
- クラウド同期（メタデータ含む）。
- 金融機関・行政サイトの高度な自動化。
- サイト別ルールの本格的な仕組み（最小限の余地のみ残す。§11b）。

## 11b. サイト別ルール（将来拡張。RFC-002 §11.3 を採用）

特定サイトについては、将来的にサイト別ルール（プロフィール編集ページURL、住所変更ページURL、
フォーム項目マッピング、注意事項）を持てるようにする。検出ロジックはモジュール化し、
ルールベース検出とヒューリスティック検出を分離して、サイト別プラグインを後から差し込める余地を残す。
**MVPではサイト別ルールは持たない**（ユーザー登録の更新ページURL＝§6b が事実上の最小ルール）。

## 12. リスク（RFC-002 §12 を統合）

| リスク | 内容 | 対策 |
| --- | --- | --- |
| `chrome://` リンク不成立 | パスワードマネージャー / Chrome設定への遷移がブロックされる可能性（§6, R） | PoC を最優先。フォールバック（URLコピー表示・案内文）を設計 |
| サイト一覧の網羅性 | 観測ベースのため、autofill を使ったことがないサイトは一覧に出ない | 手動追加を一級機能に。将来はブックマーク/履歴/CSVインポートを検討（§3b） |
| サイトごとの構造差異 | フォーム構造・更新導線がサイトごとに大きく異なり、検出が外れる | 手動確認前提・検出結果に信頼度・ユーザー補正・サイト別ルールの段階導入（§3, §11b） |
| セキュリティ上の誤解 | 「このアプリが個人情報をフルで保持している」と誤解される | UI上で保存対象/非保存対象を明示。初回起動時に説明。設定画面でデータ方針を確認可能に（§7） |
| 自動化への期待値 | 完全自動更新を期待される | 「更新支援ツール」であること・自動送信しない方針を明示。ユーザー確認を必須に（§6b, §9） |

## 13. 成功指標（RFC-002 §14 を採用）

MVP段階での成功指標:

- ユーザーが更新対象候補サイトを一覧で把握できる。
- 住所変更後に確認すべきサイトを漏れなく管理できる（各サイトの更新状況を記録できる）。
- 機微情報（カード番号・パスワード・電話フル桁・住所全文）を保存しない設計を維持できる。
- Chrome autofill と競合せず、補助ツールとして機能する。
- 少数の実サイトでフォーム検出と autofill 観測が有効に機能する。

## 14. 結論（暫定）

formfill-assistant の中核方針を「個人情報の独自管理＋自前fill」から「Chrome autofill /
Chrome Password Manager を前提とした **観測・インベントリ・更新支援**」へ転換する。
個人情報のフル保持を避けつつ（識別用の軽量値のみ保存）、ユーザーが複数サイトの登録情報更新を
体系的に進められるようにする。初期MVPは、対象サイトの可視化、更新ステータス管理、フォーム検出、
更新ページへの到達支援、Chrome 側管理画面への誘導を中心とし、完全自動更新は行わない。
