## 0. この改訂の理由（なぜ抜本転換するか）

2つの入力から方針を抜本転換する。

1. **Chrome 依存は成立しない（技術的裏付け）**: Issue #29 の実機検証で、日本（Chrome 149）の
   Chrome autofill は氏名・メールしか発火せず、住所・電話・会社名は楽天・Amazon の実フォームでも
   不発だった。調査の結果、「連絡先情報」「高精度の自動入力」は移行期機能でロケール差が大きい
   （[`research-chrome-autofill-locale-maturity.md`](research-chrome-autofill-locale-maturity.md)）。
   **Chrome autofill を製品の基盤に据える前提（旧 RFC-001/002）は崩れた。**
2. **ユーザーの意思決定（製品方針）**: 「Chrome 依存をやめ、ユーザーが自分の個人情報を自分で管理できる
   ようにする」。さらに、開発・アプリ動作の双方で **human-in-the-loop を撤廃し、AI に最大限の権限を
   与えて極力人間が介入しない**形にする（人間の介入がアイデアの限界を生むのを避け、AI の創造力を
   最大限引き出すため）。

→ 製品を「Chrome の補助・観測ハブ」から、**個人情報を自前で保持し、AI エージェントがフォーム登録・
更新を完全自動で実行するアプリ**へ転換する。

---

## 1. 製品ビジョン / 名称

- **名称**: `Catashiro`（旧 `formfill-assistant` / `autofill-assistant` を改称。"assistant"＝補助の含意を外し、
  自律実行を主役にする）。
- **一言で**: ユーザーの個人情報を一元保管し、**URL を渡すだけで AI エージェントが新規登録を完遂し、
  登録済みサイトの情報を最新に一括更新する**ローカル自律エージェント。
- **想定ユーザー**: 多数の Web サービスに登録があり、新規登録・引っ越し/連絡先変更に伴う更新を
  自分の手で繰り返したくない人。自分の個人情報を自分の管理下（ローカル）に置きたい人。

---

## 2. 設計原則

| 原則 | 内容 |
| --- | --- |
| 自前完結 | 個人情報の保存・入力・更新をすべて `Catashiro` 自身が行う。Chrome autofill / Password Manager に依存しない。 |
| ローカルファースト | データはローカルに暗号化保存。外部送信は「ユーザー契約の AI プロバイダへの必要最小限」に限る（§6, §9）。 |
| AI 最大自律 | フォーム発見・項目マッピング・入力・送信を AI エージェントが自律判断で行う。人間の事前承認は原則不要。 |
| 人間介入は最小（極力ゼロ） | 介入は「保存されていない情報の入力要求」と「設計上自動化できない壁（§10）」に限定する。 |
| 開発も同方針 | 開発判断も AI が主導し、ユーザー確認を最小化する（§11 の安全境界・法的論点を除く）。 |

> **「極力ゼロ」の例外（§10 で詳述）**: CAPTCHA・MFA・本人確認・メール/SMS 認証・最終決済など、
> 仕組み上ボットを止めるために存在する壁は **bypass しない**。これらに当たったらユーザーへ
> ハンドオフする。これは HITL への回帰ではなく、自動化が原理的に届かない箇所の安全な受け渡し。

## 3. 保管する個人情報（ユーザーデータストア）

`Catashiro` は以下を**あらかじめ保存**する。旧方針（カード・パスワード非保存）を**反転**する。

- 氏名（姓名・カナ・英字表記）
- 住所（自宅 / 勤務先 / 配送先 / 請求先。国別フォーマットに耐える構造化＋自由記述の両対応）
- 電話番号
- メールアドレス
- **クレジットカード番号**（番号・有効期限・名義・セキュリティコードの扱いは §9 で要決定）
- **各サイトごとの ID / パスワード**
- その他、登録時に動的追加される任意項目（§4 の「新項目追加」で増える）

データモデル（暫定）:

```ts
// グローバルな個人情報（サイトに依らないマスターデータ）
interface ProfileField {
  key: string;          // "name.full" / "address.home" / "card.primary.number" / "email" ...
  label: string;        // 表示名（ユーザー編集可）
  value: string;        // 暗号化して保存（§9）
  category: "name" | "address" | "phone" | "email" | "card" | "credential" | "custom";
  sensitive: boolean;   // card/credential/security-code は true。表示・ログ・送信を制限
  updatedAt: number;
}

// サイトごとに「実際に入力した値」を記録（更新差分検出の土台＝§5）
interface SiteRecord {
  origin: string;
  serviceName: string;
  registeredAt: number;
  credentialRef?: string;     // 当該サイトの ID/パスワードへの参照
  filledFields: FilledField[]; // どの項目にどのマスター値を入れたか（値の参照＋入力時点のスナップショット）
  status: "registered" | "needsUpdate" | "updated" | "failed" | "manualHandoff";
  lastUpdatedAt?: number;
}

interface FilledField {
  profileKey: string;     // 参照したマスター ProfileField.key
  filledValueHash: string;// 入力した値のハッシュ（差分検出用。実値は SiteRecord には持たない）
  fieldSelector?: string; // 観測したフォーム項目の識別子（再訪時の再現用）
  filledAt: number;
}
```

> 設計メモ: マスター値の実体は `ProfileField`（暗号化）に一元化し、`SiteRecord` 側は**参照＋ハッシュ**で
> 持つ。これで「各サイトに入れた値」と「最新マスター値」の差分を、実値を多重保存せずに検出できる（§5）。

## 4. コア機能 A: URL からの自動 新規登録（レビュー兼確認ゲート付き）

入力: ユーザーが「このサイトに登録したい」と URL を渡す。

**Q2 の決定（2026-06-12）**: 完全無確認では行わない。**送信前に1回だけ、内容をレビューできる確認
ゲート**を挟む（Google の Universal Cart / UCP の発想を参照しつつ、`Catashiro` は**新規登録のみが対象で
決済はスコープ外**）。確認後の規約承認・最終送信はエージェントが代行する。確認は**フォーム解析の後**に
出し、白紙委任ではなく送信内容のレビューを兼ねる。

エージェントの動作:

1. 渡された URL 内から**新規登録ページを自律的に探索**する（リンク文言・サイトマップ・導線パターンを AI が判断）。
2. 登録フォームを解析し、各項目に対応するマスター値（§3）をマッピングする（この時点では送信しない）。
3. 必要な情報が**未保存**なら、その項目だけユーザーに入力を促す。入力値は **`ProfileField` に新項目
   として追加**し、以後再利用する。
4. **レビュー兼確認ゲートを表示**する。最低限、次を提示する:
   - 対象サイト（オリジン）と、送信する項目（カテゴリ／どのプロフィールを使うか。例: 自宅 or 勤務先住所）。
   - 検出した**利用規約 / プライバシーポリシーのリンク**と、後述の高リスク検出の要約。
   - ユーザーは「登録する」を1クリック（＝送信内容の最終レビューを兼ねる）。
5. 承認されたら、各項目を入力し、**規約に同意して送信・登録まで完遂**する（規約承認・最終送信は代行）。
6. 完了後、`SiteRecord` を作成（status=`registered`）し、**承認レコード（mandate, §4b）を残す**。
7. CAPTCHA / MFA / メール認証等に当たった場合は §10 に従いユーザーへハンドオフ（status=`manualHandoff`）。

### 規約承認代行の3ガード（決定 2026-06-12 承認）

規約承認・最終送信をエージェント代行する既定方針に、次の安全弁を付ける。

- **ガード1: 高リスク条項のエスカレーション**: 規約から**自動更新サブスク・強制仲裁・データの
  第三者提供/販売・コンテンツ利用許諾**等を検出したら、確認ゲートに明示し、自動承認を止めて
  ユーザー判断を仰ぐ。長大な規約をユーザーが読まずに同意する認知負荷を下げ、リスクに気づける
  ようにすることが狙い（UX 向上として位置づける）。
- **ガード2: 支払い項目の検出で停止（例外あり）**: 登録フォームに**カード/支払い**項目を検出したら
  原則は自動進行せず停止・ハンドオフ（即時購入・チェックアウトはスコープ外）。
  - **例外（無料トライアル → サブスク課金）**: 「無料トライアル後に課金が始まる」型は**ガード1の
    高リスク条項としてユーザーに確認**する。ユーザーが将来課金を承認した場合に限り、**クレジット
    カードの登録を自動で行う**。すなわちこの型では高リスク確認＝将来課金への同意であり、承認後は
    保存カードを自動入力してよい。
  - 区別の要件: 「無料トライアル → 後日サブスク課金」と「その場で即時決済・購入」を取り違えると、
    即時課金にカードを自動入力する事故になる。両者を確実に区別する判定基準を実装時に定義する（§13 Q2a）。
- **ガード3: 資格・本人性の表明は自動チェックしない**: 「18歳以上」「在住」「正規の権限を持つ」等の
  eligibility 系チェックは事実の表明のため、自動でチェックせず提示してユーザーに委ねる。

### 自動アカウント作成を禁止しているサイト（Q2c 決定）

ToS で自動アカウント作成を禁止しているサイトでは、**個人情報の自動入力までは行い、最終登録は自動送信
しない**。ユーザーに「このサイトは自動アカウント作成を禁止しているため、最後の登録ボタンはご自身で
押してください」と説明し、**最終登録ボタンはユーザー本人に押してもらう**。これにより、規約・bot 検知を
欺く方向には踏み込まず、入力の手間だけを肩代わりする（assisted fill）。

## 4b. 承認レコード（mandate）— AP2 の発想を借用

エージェントがユーザーに代わって規約承認・登録を行うため、**何を承認したかを監査可能に残す**。

```ts
interface RegistrationMandate {
  origin: string;
  authorizedAt: number;        // ユーザーが確認ゲートで承認した時刻
  profileSnapshotRef: string;  // 使用したプロフィール群への参照（実値は持たない）
  submittedFieldKeys: string[];// 送信した ProfileField.key の一覧（値は持たない）
  termsUrl?: string;           // 同意した規約/ポリシーのURL
  termsVersionHash?: string;   // 取得時点の規約本文のハッシュ（バージョン同定）
  highRiskFlags?: string[];    // 検出してユーザーが承認した高リスク項目
  result: "registered" | "failed" | "manualHandoff";
}
```

> §9 のデータ方針に従い、mandate も**実値を持たず参照＋ハッシュ＋規約URL**で構成する。ユーザー保護
> （何にいつ同意したかの証跡）と不具合調査の両方に使う。

## 5. コア機能 B: サイト別インベントリ＋最新情報への一括更新

UI: サイト一覧。各行＝登録済みサイト。各サイトで**入力済みの各項目を確認**できる。

- 各行にチェックボックス。**全選択**も可能。
- 「**最新の個人情報にアップデートする**」ボタン。
- 動作: 選択した全サイトについて、`SiteRecord.filledFields` のハッシュと**最新マスター値（§3）の
  ハッシュを突き合わせ、差分のある項目を検出**。差分のあるサイトをエージェントが順に開き、
  当該項目だけを最新値で**修正・更新（保存まで）**する。
- 進捗・結果を行ごとに反映（updated / failed / manualHandoff）。

差分検出は値比較ではなくハッシュ比較なので、`SiteRecord` に実値を多重保存せずに「古い情報のサイト」を
特定できる（§3 の設計メモ）。

一括更新中に CAPTCHA/MFA/再認証に当たった場合は、§10b に従い**そのサイトだけ一時停止 → 人間が解決 →
同一セッションで自動入力を再開 → 次サイトへ**（pause-resume）。

## 6. AI エージェント構成

- **ユーザー自身が契約している AI を使う**。`Catashiro` の設定画面で**ユーザーが API キーを入力**する。
- API キーはローカルに暗号化保存（§9）。送信先はユーザーが選んだプロバイダのみ。

### 対応プロバイダ / モデル（Q5 決定 2026-06-12）

初期対応は以下に限定。プロバイダ抽象化レイヤを設け、後から追加できる構造にする。

| プロバイダ | モデル |
| --- | --- |
| Anthropic | Claude Opus / Sonnet / Haiku |
| OpenAI | GPT-5.4 / GPT-5.4-mini / GPT-5.3-Codex |

> 厳密な API モデルID（Claude の `claude-opus-*` 等の snapshot 文字列、GPT-5.x 系の正式ID）は
> 実装時に各社ドキュメントで確認してピン留めする。

### モデルへの個人情報開示の最小化（Q4 決定 2026-06-12）

**原則: 個人情報の実値はモデルに渡さない。** モデルの役割は「フォーム理解（どの欄が何か・登録ページの
発見・高リスク条項の検出）」であり、値そのものの取り扱いではない。

- **構造はモデルへ、値はローカルで**: モデルにはフォーム構造（ラベル・`name`・type・周辺テキスト）と
  規約テキストを渡し、**マッピング計画**（「欄3=自宅郵便番号」「送信ボタン=…」「高リスク=自動更新」）を
  受け取る。**実値の流し込みは Playwright 層がローカルで行い、モデルには送らない**（§7）。
- どうしても値を渡す必要がある場合（住所整形等）は、プレースホルダ/トークンで送ってローカルで置換、
  または最小限のマスク値に限る。
- **ステートフル機能を使わない**: プロンプトキャッシュ・保存スレッド・プロバイダのメモリ機能に
  個人情報を載せない（プレーンなステートレス補完のみ）。
- 可能なら各社の**ゼロデータ保持 / 学習不使用オプション**を選ぶ。

> モデルが個人情報をどこにどれだけ保持するか（補足説明）: 大手の推論API（Anthropic / OpenAI）は
> **モデル重みに学習・記憶しない**（推論で重みは変わらない）。**コンテキストウィンドウはリクエスト毎に
> 揮発**し、応答後にモデル側が保持するものではない。残存リスクは (1) プロバイダ側の不正利用監視のための
> **リクエストログ保持**（各社ポリシー。多くは一定期間。ゼロ保持契約で無効化できる場合あり）、
> (2) 自分が**明示的に有効化したステートフル機能**（キャッシュ・保存スレッド・メモリ）。本設計は
> (2) を使わず、(1) は最小開示（値を送らない）で実害を抑える。各社ポリシーは変わるため実装時に最新を確認。

### ツール使用 / 権限

- モデルにはブラウザ操作を**直接は与えず**、「計画を返す→ローカルの Playwright 層が実行」の分離を基本と
  する（値をモデルに握らせない設計と整合）。エージェント的なツール使用の範囲は実装時に詰める（§13 残）。

## 7. アーキテクチャ（Q1 決定 2026-06-12）

- **形態: Playwright ベースのローカルアプリ**に確定。Chrome 拡張（MV3）は採らない。
  - 理由（ユーザー決定）: **ブラウザエンジン非依存**にしたい。Playwright は Chromium / Firefox /
    WebKit（Safari エンジン）を横断操作できるため、Chrome 専用技術に縛られない。
  - 副次的利点: 完全自動登録・自動送信は MV3 content script の制約（手動 fill 前提 API、`isTrusted`）と
    相性が悪い。Playwright なら制御ブラウザ上で自然に入力・送信できる。
  - **前提の注記**: Playwright は自前のブラウザバイナリを起動して操作する。操作対象はユーザー日常の
    Safari.app / Firefox.app の既存セッションではなく**制御用ブラウザ**。登録は新規セッションで、更新は
    保存済み資格情報（§3）でログインして行う。「拡張」ではなく「代行する制御ブラウザ」モデル。
- 層:
  - **ストア層**: 暗号化された `ProfileField` / `SiteRecord` / `RegistrationMandate`（ローカル）。
  - **エージェント層**: ユーザーの AI（§6）＋フォーム探索・項目マッピング・高リスク条項検出の判断。
  - **自動操作層**: **Playwright** でブラウザを操作（ナビゲート・入力・送信・観測）。エンジン横断。
  - **UI 層**: 個人情報管理画面、サイト一覧（§5）、確認ゲート（§4）、設定（API キー等）。

## 8. PoC 計画（実サイトを使わない）

実サイトは使わず、**ローカルの Web サーバーとして起動するテストサイトを約10パターン**作成する。
**エージェントのフォーム操作・自動テストとも Playwright を使う**（§7。Chromium / Firefox / WebKit で
横断検証し、ブラウザエンジン非依存を確認する）。**PoC のフォーム検出ロケールは日本語のみ**（Q7。
多言語は後続）。

**2バージョンを作って精度比較する（Q8 決定）**:
1. **決定的版**: 既存の #9 scanner（`scanFields`）＋ #10 分類ロジックを流用してフォーム種別を判定する。
2. **AI 版**: フォーム構造の理解・マッピングを AI モデル（§6）に委ねる。
両版で新規登録・自動更新の成功率／誤マッピング率を測り、**どちらが精度が高いか**を比較する。まず 1 を
作り、その後 2 を作る。

- 各テストサイトは「**ユーザー登録ページ**」と「**登録情報の編集ページ**」だけを持つ最小構成。
- **サイトごとにフォームのフォーマットを変える**（項目順・ラベル文言・`name`/`id` 規則・必須/任意・
  分割住所/単一住所・select/radio/checkbox・多段ステップ・動的描画 等）。どんなフォーマットでも
  自動入力できるかを検証する。
- **確認ゲート系の検証用に、次の特性を持つテストサイトを混ぜる**（§4 の3ガードを検証する）:
  - **規約同意つきサイト**: 規約への同意文＋同意ボタンを持ち、本文に高リスク条項（自動更新・
    第三者提供等）を含む。→ 高リスク条項を抽出してユーザーに提示できるかを検証。
  - **無料トライアル → サブスク課金サイト**: 登録時にカード項目があり、無料期間後に課金が始まる旨を
    記載。→ 高リスク警告を表示し、ユーザー承認後にカード自動入力へ進めるかを検証（ガード2の例外）。
  - **自動アカウント作成禁止サイト**: 規約に自動作成禁止を明記。→ 入力までで止め、説明して最終登録
    ボタンをユーザーに委ねられるかを検証（Q2c）。
- 検証シナリオ:
  1. **新規登録**: URL を渡す→登録ページ発見→全項目入力→確認ゲート→送信完遂（§4）。
  2. **自動更新**: 登録済み情報をマスター値変更後に差分検出→該当サイトを更新（§5）。
- すべて **localhost の Web サーバー**で完結（外部ネットワーク・実 PII 不使用・CAPTCHA/MFA なし）。
- 目的: フォーマット頑健性、エージェントのフォーム理解精度、確認ゲート/3ガードの動作、エンジン横断の
  動作、失敗時の挙動を見極める。
- データはすべて**ダミー**。規約・課金・禁止条項もテスト用の作り物（実サイトの壁は §10 で別途）。

> PoC がローカル限定なので、実 CAPTCHA/決済/本人確認には触れず、テスト用に作った規約・課金・禁止条項で
> 確認ゲートと3ガードの挙動まで安全に検証できる。

## 9. セキュリティ / プライバシー

フル PII＋カード番号＋セキュリティコード＋サイト別パスワードを保持するため、**保護要件は旧方針より
格段に重くなる**。

- **ローカルのみ**: 個人情報はローカル保存。外部送信は §6 のユーザー契約 AI への必要最小限のみ。
  テレメトリ・解析送信は行わない。
- **モデルへの最小開示**: 個人情報の実値を AI モデルへ送る範囲を最小化（§6）。
- **ログ非出力**: 個人情報・カード・パスワード・API キーを console/エラー/クラッシュ情報に出さない。

### 暗号化方式（Q3 決定 2026-06-12）

「すべて暗号化し、平文では決して保存しない」を満たす標準的な構成を採る。すべて広く検証された
アルゴリズムのみで、独自実装はしない。

1. **マスターパスフレーズ**: ユーザーが起動時に1つ入力する。これだけが平文の起点で、保存しない。
2. **鍵導出（KDF）**: マスターパスフレーズ＋ランダムな salt（16バイト、保存する）から
   **Argon2id**（メモリハードで総当たりに強い）でマスター鍵を導出する。Argon2 のネイティブ依存を
   避けたい場合の代替は **PBKDF2-HMAC-SHA-512（反復回数 ≥ 60万）**。パラメータは保存して再現可能にする。
3. **暗号化**: 各レコード値を **AES-256-GCM**（認証付き暗号。改ざん検知込み）で暗号化。
   **レコード毎にランダムな IV（96bit）** を使い使い回さない。保存形式は `{salt, kdfParams,
   records: [{iv, ciphertext+tag}]}`。
4. **マスター鍵の寿命**: 導出した鍵は**アンロック中だけメモリ保持**し、ディスクに書かない。
   ロック/終了でメモリから破棄する。
5. **実行環境**: Web Crypto API（Node / ブラウザ共通）で AES-GCM・PBKDF2 を、Argon2id は検証済み
   ライブラリ（`hash-wasm` 等）で行う。

利便性オプション（任意）: 毎回のパスフレーズ入力を避けたい場合、**OS のキーチェーン**（macOS Keychain /
Windows DPAPI / Linux libsecret）にセッション用の鍵をラップして預ける。利便性と引き換えに、OS ログイン
セッションが鍵を守る前提になる（トレードオフを設定で明示）。

**カードのセキュリティコード（CVV）について（ユーザー判断で保存する）**:
- 一般にカード会社/PCI 基準は CVV の保存を**非推奨**とする。理由は、番号が漏れても CVV が無ければ
  悪用しにくい「最後の砦」だから。これは**個人が自分のカードを自分用に保存する**ケースには直接は
  かからないが、リスクの考え方は同じ。
- ユーザーの希望どおり保存するが、**最も機微なフィールド**として扱う:
  上記の暗号化に加え、(a) AI モデルには絶対に送らない（§6）、(b) fill する瞬間にだけ復号し直ちに破棄、
  (c) カード操作時はマスターパスフレーズ再入力を求めるオプションを既定 ON とする（§13 Q3 で調整）。

### 鍵を忘れた場合 / バックアップ

- ゼロ知識設計（パスフレーズのみ）だと、忘れると全データ復号不能。**リカバリキー**（一度だけ表示する
  長いランダム文字列）を発行し、ユーザーが安全に保管できるようにする。エクスポート/バックアップの
  暗号化形式も同じ鍵体系に揃える。詳細形式は §13 Q3 残として実装時に確定。

## 10. 制約・安全境界・未解決リスク

「AI 最大自律・人間介入ゼロ」と「実サイトでの登録/更新」は一部両立しない。原理的な壁を明記する。

| 壁 | なぜ自動化できないか | 方針 |
| --- | --- | --- |
| CAPTCHA / bot 検知 | ボットを止めるための仕組み。bypass は規約違反かつ本プロジェクトの禁止事項 | **bypass しない**。検知したらユーザーへハンドオフ |
| MFA / OTP / 本人確認 | ユーザー本人の所持要素が必要 | ユーザーへハンドオフ |
| メール/SMS 認証リンク | 受信箱/端末アクセスが必要 | ユーザーへハンドオフ |
| 利用規約・同意の承諾 | 法的同意。自動チェックは責任問題 | **代行する**（§4）。ただし確認ゲートで規約リンク＋高リスク要約を提示し、高リスク条項は自動承認を止める（§4 の3ガード） |
| 最終送信（登録） | アカウント作成＝契約 | **代行する**。ただし§4 のレビュー兼確認ゲートをユーザーが承認した後のみ |
| 決済・支払い | 決済＝金銭債務 | **原則スコープ外**（即時購入・チェックアウトは停止・ハンドオフ）。**例外**: 無料トライアル→サブスク課金は高リスク条項として確認し、承認時のみカード自動登録（§4 ガード2） |

法的・規約上の論点（実装前に要整理）:

- 自動の新規登録は、サイトによっては自動化禁止（ToS）に該当しうる（§13 Q2c）。
- 登録での誤入力・規約の代行承諾は**ユーザー自身に法的責任**が生じる。§4 のレビュー兼確認ゲート＋
  3ガード＋承認レコード（§4b）で、白紙委任・規約事故・意図しない課金を抑える。PoC（§8）はローカルで
  これらの壁に触れず中核能力のみ検証する。

### 10b. CAPTCHA / MFA の検知とシームレスなハンドオフ（Q6 決定 2026-06-12）

**検知方法（保守的・UI 指向。bypass は一切しない）**:

- **CAPTCHA**: 既知ウィジェットの DOM シグナルを検出する。reCAPTCHA（`iframe[src*="recaptcha"]` /
  `.g-recaptcha`）、hCaptcha（`.h-captcha`）、Cloudflare Turnstile（`.cf-turnstile` /
  `challenges.cloudflare.com`）、Arkose/FunCaptcha 等。加えて可視テキスト（「私はロボットではありません」
  「認証」）。**解かない。存在を検出したら停止**するだけ。
- **MFA / OTP**: 入力欄の特徴（`autocomplete="one-time-code"`、数字1桁ボックス群、`name`/`id`/`label` に
  "otp" / "認証コード" / "ワンタイム" / "verification code" / "2段階"）とページ文言で検出。
- **メール/SMS 認証**: 「確認メールを送信しました」「コードを送信」等の文言で検出。
- **判定方針**: 決定的な DOM ヒューリスティックを一次シグナルにする（速く・PII をモデルに送らない）。
  迷う場合は**停止側に倒す**（誤検知＝人間に聞く方が、自動進行より安全）。補助的にモデルへ
  「このページは人間の操作が必要か」を構造情報だけで分類させてもよい（値は送らない、§6）。

**シームレスなハンドオフ＆再開**:

- Playwright は**ヘッド付き（headed）**で起動し、エージェントが操作しているのと**同一のブラウザ
  セッション**をユーザーがそのまま触れる。検知時:
  1. エージェントは自動操作を一時停止し、そのウィンドウを前面化、オーバーレイで指示を出す
     （例:「MFA コードを入力し、完了したら『続行』を押してください」）。
  2. ユーザーが**同じセッション**で CAPTCHA/MFA を解決（cookie・セッションは保持される）。
  3. ユーザーが「続行」を押すと、エージェントは**中断した手順から自動入力を再開**する。次に入れる欄等の
     進行状態はページではなくエージェントが保持しているため、再開はクリーンに行える。
- **一括更新中（§5）**: あるサイトで検知したらそのサイトだけ一時停止 → 人間が解決 → 同セッションで
  そのサイトの自動入力を再開 → 完了後に次のサイトへ進む（pause-resume を同一 Playwright コンテキストで
  行う。run ループは「人間完了」シグナルを await する）。
- 注意点: 人間は**エージェントの制御ブラウザ**で操作する必要がある（自分の日常ブラウザではセッションが
  繋がらない）。§7 の「制御ブラウザ」モデルと整合。

## 11. 現行 docs（CLAUDE.md / AGENTS.md）との矛盾点

本 RFC が合意されたら、以下を docs 追従更新Issueで反映する必要がある（**現時点では未更新**）。

| 現行原則（CLAUDE.md / AGENTS.md） | 本 RFC での変更 |
| --- | --- |
| Human-in-the-loop が中核 | **撤廃**（AI 最大自律。介入は §10 の壁のみ） |
| 自動フォーム送信をしない | **行う**（完全自動登録・更新。§4, §5） |
| 自動アカウント登録をしない | **行う**（§4） |
| パスワードを保存しない | **保存する**（暗号化。§3, §9） |
| クレジットカード情報を保存しない | **保存する**（CVV 含む。暗号化＋最重要扱い。§3, §9） |
| ローカルに最小限のみ保持 | **フル PII を保持**（暗号化前提。§3, §9） |
| 自律ブラウザAIエージェントは非対象 | **中核**（§4〜§7） |
| バックエンド/AI 分類を入れない | AI エージェント（ユーザー契約・ローカル経由）を導入（§6） |

| 名称 formfill-assistant | **`Catashiro` に改称**（§1） |

> 不変で維持するもの: **CAPTCHA/MFA/bot 検知を bypass しない**（§10）。ローカルファースト・
> 外部テレメトリ無し（§9）。

## 12. 旧方針（v1/v2）からの差分まとめ

| 観点 | 旧（Chrome 補助ハブ） | 新（自律エージェント） |
| --- | --- | --- |
| データ保持 | 軽量識別値のみ（郵便番号・下4桁） | フル PII＋カード＋パスワード（暗号化） |
| 入力主体 | Chrome autofill（ユーザー操作） | `Catashiro` のエージェント（自動） |
| 送信 | ユーザーが押す | エージェントが自動送信 |
| 人間の役割 | 中核（HITL） | 最小（§10 の壁のみ） |
| Chrome 依存 | 前提 | なし |
| AI | 使わない（決定的ルール） | ユーザー契約 AI が中核 |

  承認後の規約承諾・最終送信はエージェント代行、決済は原則スコープ外（§4, §10）。3ガードは承認済み。
  残る小論点:
  - **Q2a**: 高リスク条項の検出語彙・要約の精度、および「無料トライアル→サブスク課金」と「即時決済」の
    判定基準（ガード2の例外を安全に効かせるため）。作り込み度は PoC 後に詰める。
  - **Q2b（決定）**: 3ガードを**有効で採用**。既定の強さ・ユーザー設定可否の細部は実装時に調整。
  - **Q2c（決定）**: 自動化禁止 ToS サイトは**入力までで止め、説明して最終登録はユーザーが押す**（§4）。
- **Q3（決定済み 2026-06-12）**: CVV も保存する。暗号化は **Argon2id（代替 PBKDF2-SHA-512 ≥60万回）＋
  AES-256-GCM**、マスターパスフレーズで鍵導出、鍵はメモリのみ、リカバリキー発行（§9）。残: CVV の
  再認証 ON の細部、バックアップ形式。
- **Q4（決定済み 2026-06-12）**: 個人情報の実値はモデルに渡さない（構造はモデル／値はローカル Playwright）。
  ステートフル機能不使用・ゼロ保持優先（§6）。モデルの保持期間の補足説明も §6 に記載。
- **Q5（決定済み 2026-06-12）**: Anthropic（Opus/Sonnet/Haiku）と OpenAI（GPT-5.4/5.4-mini/5.3-Codex）に
  限定。プロバイダ抽象化レイヤ。厳密な API モデルIDは実装時に確認（§6）。
- **Q6（決定済み 2026-06-12）**: DOM ヒューリスティックで CAPTCHA/MFA/メール認証を検知（解かない）、
  headed Playwright の同一セッションで人間が解決→エージェントが中断点から再開（pause-resume）。一括更新も
  同方式（§10b, §5）。
- **Q7（決定済み 2026-06-12）**: PoC のフォーム検出ロケールは**日本語のみ**。多言語は後続（§8）。
- **Q8（決定済み 2026-06-12）**: PoC は**決定的版（#9/#10 流用）と AI 版の2本**を作り精度比較。まず
  決定的版（§8）。
