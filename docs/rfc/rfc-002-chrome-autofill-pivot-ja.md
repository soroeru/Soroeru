# RFC-002: Chrome Autofill を前提とした Formfill Assistant 要件定義

> **注記（2026-06-11）: 本ドキュメントは非規範（歴史的資料）。正は
> [`rfc-001-chrome-autofill-pivot.md`](rfc-001-chrome-autofill-pivot.md)。**
>
> 本ドキュメントは要件のインプットとして作成され、内容は RFC-001 に統合済み。本ドキュメントと
> RFC-001 が食い違う場合は RFC-001 に従うこと。特に次の2点は RFC-001 §0 の判断で**置き換え済み**:
>
> 1. 「Chrome Password Manager の保存URLからサイト一覧を作成する」（§3.2, §7.1, §8.1, §10.1）
>    → 拡張の公開APIでは保存URL一覧を取得できないため、**autofill 観測を一次ソース＋手動追加を補完**
>    に変更（RFC-001 §3b）。
> 2. 「氏名・電話・メール・住所を保存しない」（§8.6, §11.1）→ **カテゴリ別の軽量識別値
>    （名前=フル・電話=下4桁・住所=郵便番号のみ）を保存する**方針に変更（RFC-001 §5）。
>    カード番号・パスワード・電話フル桁・住所全文を保存しない原則は共通で維持。

## 1. 概要

本ドキュメントは、`formfill-assistant` における要件を整理するものである。

当初の構想では、ユーザーの住所・氏名・電話番号・メールアドレスなどの個人情報をアプリ側で一元管理し、複数サイトの登録情報を横断的に更新することを想定していた。しかし、セキュリティ、プライバシー、実装難易度、ユーザーの信頼性を考慮し、方針を変更する。

本RFCでは、Chrome Autofill および Chrome Password Manager を既存の安全基盤として活用し、本アプリは「保存済みサイトの把握」「更新対象の可視化」「更新作業の支援」に集中する方針を定義する。

## 2. 背景

ユーザーが引っ越しや電話番号変更などを行った場合、ECサイト、金融サービス、公共サービス、会員サイトなど、多数のWebサイトに登録された個人情報を個別に更新する必要がある。

現状では、次のような課題がある。

- どのサイトに古い住所や連絡先が登録されているか把握しづらい
- Chrome Autofill はフォーム入力を補助できるが、複数サイトの登録情報を一括管理・更新する機能はない
- Chrome Password Manager はログイン情報を保持しているが、登録済みサイトのプロフィール情報更新までは扱わない
- サイトごとにフォーム構造や更新画面の導線が異なるため、更新漏れが発生しやすい
- 個人情報を独自アプリに保存すると、セキュリティリスクと信頼性の問題が大きい

このため、本アプリでは「個人情報そのものを保持する」のではなく、Chrome の既存機能を前提に、ユーザーが安全に登録情報更新を進められる補助ツールを目指す。

## 3. 方針転換

### 3.1 旧方針

旧方針では、アプリ側にユーザーの標準プロフィール情報を保存し、それを各サイトのフォームにマッピングして更新する構想だった。

想定していた管理対象は次のような情報である。

- 氏名
- 住所
- 電話番号
- メールアドレス
- クレジットカード情報
- その他 Chrome Autofill が扱える個人情報

### 3.2 新方針

新方針では、個人情報の一次管理は Chrome Autofill に委ねる。

本アプリは、次の役割に限定する。

- Chrome Password Manager に保存されたURLを、更新対象候補サイトの一覧として利用する
- 各サイトのプロフィール・住所・支払い情報などの更新画面を検出または案内する
- Chrome Autofill が入力可能なフォーム項目を検出する
- 更新対象候補を一覧化する
- ユーザーに手動確認・手動更新を促す
- 必要に応じて Chrome の設定画面または管理画面へのリンクを提供する

アプリ側は、原則として住所・氏名・電話番号・メールアドレス・クレジットカード情報などの個人情報を永続保存しない。

## 4. 目的

本アプリの目的は、ユーザーが複数サイトに登録している個人情報を安全かつ効率的に更新できるよう支援することである。

特に、次の価値を提供する。

- 更新すべき可能性のあるサイトを可視化する
- 更新漏れを減らす
- Chrome Autofill を使った入力作業を補助する
- サイトごとの更新画面への到達を支援する
- 個人情報をアプリ側で保持しないことで、セキュリティリスクを抑える

## 5. 非目的

本アプリは、少なくとも初期段階では次のことを目的としない。

- 各サイトの登録情報を完全自動で更新すること
- ユーザーの同意なしにサイトへログインすること
- ID・パスワードを取得・保存・送信すること
- クレジットカード番号などの機微情報をアプリ側で保存すること
- サイトの利用規約に反するスクレイピングや自動操作を行うこと
- Chrome Autofill や Chrome Password Manager を置き換えること
- 金融機関や行政サービスなど高リスクサイトの完全自動更新を行うこと

## 6. 想定ユーザー

主な想定ユーザーは、次のような個人ユーザーである。

- 引っ越しに伴い、多数のWebサービスで住所変更が必要な人
- 複数のECサイトや会員サイトを利用している人
- 登録情報の更新漏れを避けたい人
- Chrome Autofill や Chrome Password Manager を日常的に利用している人
- 自分の個人情報を新しいアプリに保存することには抵抗がある人

## 7. ユースケース

### 7.1 住所変更時の更新対象確認

ユーザーは引っ越し後、Chrome Autofill 上の住所を新住所に更新する。

その後、本アプリを起動し、Chrome Password Manager に保存されているサイト一覧をもとに、住所変更が必要な可能性のあるサイトを確認する。

アプリは、各サイトについて次のような情報を表示する。

- サイト名
- URL
- ログインページ
- アカウント設定ページまたはプロフィール編集ページの候補
- 住所フォームが存在する可能性
- 更新状況
- ユーザーによる確認メモ

### 7.2 サイト別の手動更新支援

ユーザーは一覧から対象サイトを選択する。

アプリは当該サイトを開き、ユーザーがログイン後、プロフィール編集画面または住所変更画面に進めるよう支援する。

フォーム入力自体は Chrome Autofill に委ねる。

アプリは、必要に応じてフォーム項目の検出や入力候補の確認を行うが、最終的な送信はユーザーが明示的に行う。

### 7.3 更新済みサイトの記録

ユーザーが特定サイトの更新を完了したら、アプリ上で「更新済み」として記録する。

記録対象は、個人情報そのものではなく、次のようなメタデータに限定する。

- サイトURL
- 更新ステータス
- 最終確認日時
- 更新対象カテゴリ
- ユーザーメモ

## 8. 機能要件

### 8.1 サイト一覧取得

アプリは、Chrome Password Manager に保存されているURLをもとに、更新対象候補となるサイト一覧を作成する。

要件:

- 保存済みURLを取得できること
- URLをドメイン単位で集約できること
- 重複URLを統合できること
- 明らかに対象外のURLを除外または非表示にできること
- ユーザーが対象サイトを手動で追加・削除できること

注意:

- ID・パスワードは取得しない
- 認証情報は Chrome Password Manager に委ねる

### 8.2 更新対象カテゴリ管理

アプリは、サイトごとに更新対象カテゴリを管理できる。

初期カテゴリは次の通り。

- 住所
- 氏名
- 電話番号
- メールアドレス
- 支払い情報
- 配送先住所
- 請求先住所
- その他

### 8.3 Chrome Autofill 連携

アプリは、Chrome Autofill に保存された情報を前提にフォーム入力を支援する。

要件:

- Chrome Autofill が扱う標準的なフォーム項目を対象とする
- アプリ側に個人情報を永続保存しない
- 必要に応じて Chrome の Autofill 設定画面への導線を提供する
- ユーザーが Chrome 側で情報を編集できるようにする

対象となる代表的な情報:

- 氏名
- 住所
- 郵便番号
- 国・地域
- 電話番号
- メールアドレス
- クレジットカード情報

### 8.4 フォーム検出

アプリは、サイト上のフォーム構造を解析し、Chrome Autofill と対応しうる項目を検出する。

検出に利用する情報:

- HTML の `autocomplete` 属性
- input 要素の `name`
- input 要素の `id`
- label 要素
- placeholder
- 周辺テキスト
- 日本語ラベル
- 英語ラベル
- DOM構造

検出対象:

- 住所入力フォーム
- プロフィール編集フォーム
- 配送先住所フォーム
- 請求先住所フォーム
- 支払い情報フォーム
- メールアドレス変更フォーム
- 電話番号変更フォーム

### 8.5 更新画面への誘導

アプリは、対象サイトの更新画面への到達を支援する。

要件:

- ログインページを開けること
- アカウント設定ページ候補を提示できること
- プロフィール編集ページ候補を提示できること
- ユーザーが発見した正しい更新ページURLを保存できること
- 次回以降、そのURLを優先表示できること

### 8.6 更新ステータス管理

アプリは、サイトごとに更新作業の状態を管理する。

ステータス例:

- 未確認
- 更新必要
- 更新不要
- 更新済み
- ログイン不可
- 手動確認が必要
- 対象外

保存する情報:

- サイトURL
- ステータス
- 最終確認日時
- 更新カテゴリ
- メモ

保存しない情報:

- 住所
- 氏名
- 電話番号
- メールアドレス
- クレジットカード番号
- パスワード

### 8.7 ユーザー確認と送信制御

アプリは、各サイトのフォーム送信を自動では行わない。

要件:

- 最終的な更新内容の確認はユーザーが行う
- 送信ボタンのクリックはユーザー操作を原則とする
- アプリは入力補助・検出・案内に留める
- 高リスクサイトでは自動化をさらに制限する

## 9. 非機能要件

### 9.1 セキュリティ

- 個人情報をアプリ側で永続保存しない
- ID・パスワードを取得しない
- クレジットカード番号を保存しない
- 必要最小限の権限のみを要求する
- 拡張機能の権限は明示的に説明する
- 一時的に取得したデータはメモリ上のみで扱う
- ログに個人情報を出力しない
- エラー情報にも個人情報を含めない

### 9.2 プライバシー

- ユーザーが何の情報にアクセスされるか理解できること
- 初回起動時に権限とデータ利用方針を明示すること
- ユーザーが対象サイトを除外できること
- ユーザーが保存済みメタデータを削除できること
- 外部サーバーへの送信は原則行わない
- 将来的にサーバー連携を行う場合は、明示的な同意を必須とする

### 9.3 ユーザビリティ

- 更新対象サイトを一覧で確認できること
- 優先度やステータスで絞り込めること
- サイトごとに次に取るべき操作が分かること
- Chrome 側で編集すべき情報と、サイト側で更新すべき情報を区別して表示すること
- 誤って個人情報をアプリに保存しているように見えないUIにすること

### 9.4 保守性

- サイト固有ルールを追加できる設計にする
- フォーム検出ロジックをモジュール化する
- ルールベース検出とヒューリスティック検出を分離する
- 将来的にサイト別プラグインを導入できる余地を残す

### 9.5 法的・規約面

- 各サイトの利用規約に反する自動操作を避ける
- ユーザーの明示的操作を重視する
- スクレイピングや自動送信は初期MVPでは行わない
- 金融・行政・医療系サイトなどは慎重に扱う

## 10. MVP範囲

初期MVPでは、次の範囲に限定する。

### 10.1 含めるもの

- Chrome拡張機能として実装
- Chrome Password Manager の保存URLをもとに対象候補一覧を作成
- サイトをドメイン単位で整理
- サイトごとの更新ステータス管理
- 更新対象カテゴリの手動設定
- Chrome Autofill 設定画面への導線
- サイトのログインページまたは設定ページへのリンク管理
- フォーム検出の初期実装
- ユーザーによる手動更新完了記録

### 10.2 含めないもの

- 完全自動ログイン
- 完全自動送信
- ID・パスワード取得
- クレジットカード番号の保存
- 個人情報のクラウド同期
- サイト横断の自動更新実行
- 金融機関や行政サイトの高度な自動化

## 11. 技術方針

### 11.1 アーキテクチャ

想定構成:

- Chrome Extension
- Content Script
- Background Service Worker
- Local Storage または IndexedDB
- Optional: サイト別ルール定義ファイル

保存対象:

- サイトURL
- ドメイン
- 更新ステータス
- 更新カテゴリ
- 更新画面URL候補
- ユーザーメモ
- 最終確認日時

保存しない対象:

- 住所
- 氏名
- 電話番号
- メールアドレス
- クレジットカード情報
- ID
- パスワード

### 11.2 フォーム検出ロジック

検出は段階的に行う。

1. `autocomplete` 属性による検出
2. label / placeholder / name / id によるルールベース検出
3. 日本語・英語のキーワード辞書による検出
4. DOM構造に基づく補助判定
5. ユーザーによる手動補正

### 11.3 サイト別ルール

特定サイトについては、将来的にサイト別ルールを持てるようにする。

例:

- プロフィール編集ページURL
- 住所変更ページURL
- 配送先住所ページURL
- フォーム項目マッピング
- 注意事項

ただし、MVPではサイト別ルールは最小限に留める。

## 12. リスク

### 12.1 Chrome Password Manager 連携の制約

Chrome拡張機能から保存済みパスワードやURL一覧にどこまでアクセスできるかには制約がある可能性がある。

必要に応じて、代替案を検討する。

代替案:

- ユーザーが対象サイトを手動インポートする
- Chrome のエクスポート機能を利用する
- ブラウザ履歴やブックマークから候補を作る
- ユーザーがCSVで対象サイト一覧を投入する

### 12.2 サイトごとの構造差異

各サイトのフォーム構造は大きく異なる。

対策:

- 初期は手動確認を前提にする
- 検出結果に信頼度を付ける
- ユーザーが補正できるようにする
- サイト別ルールを段階的に追加する

### 12.3 セキュリティ上の誤解

ユーザーが「このアプリが個人情報を保持している」と誤解する可能性がある。

対策:

- UI上で保存対象と非保存対象を明示する
- 初回起動時に説明する
- 設定画面でデータ利用方針を確認できるようにする

### 12.4 自動化への期待値

ユーザーが完全自動更新を期待する可能性がある。

対策:

- MVPでは「更新支援ツール」であることを明示する
- 自動送信はしない方針を明示する
- ユーザー確認を必須にする

## 13. 未決事項

- Chrome拡張機能から保存済みURL一覧を安全に取得できるか
- Chrome Autofill の保存データをどこまで参照できるか
- Chrome の設定画面への直接リンク方法
- URL取得が制限される場合の代替UX
- サイト別ルールをどの形式で管理するか
- MVPで対象とするサイトカテゴリ
- 金融・行政・医療系サイトを初期対象に含めるか
- 更新ステータスをローカルだけで保持するか、将来的に同期するか
- `.me` 拡張子ではなく `.md` に統一するか

## 14. 成功指標

MVP段階での成功指標は次の通り。

- ユーザーが更新対象候補サイトを一覧で把握できる
- ユーザーが住所変更後に確認すべきサイトを減らさず管理できる
- ユーザーが各サイトの更新状況を記録できる
- アプリが個人情報を保存しない設計を維持できる
- Chrome Autofill と競合せず、補助ツールとして機能する
- 少数の実サイトでフォーム検出が有効に機能する

## 15. 結論

本RFCでは、`formfill-assistant` の中核方針を「個人情報の独自管理」から「Chrome Autofill と Chrome Password Manager を前提とした更新支援」へ転換する。

この方針により、個人情報をアプリ側で保持するリスクを避けつつ、ユーザーが複数サイトの登録情報更新を体系的に進められるようにする。

初期MVPでは、完全自動更新ではなく、対象サイトの可視化、更新ステータス管理、フォーム検出、Chrome Autofill への誘導を中心に実装する。
